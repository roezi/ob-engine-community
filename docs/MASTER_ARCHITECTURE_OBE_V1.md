# Master Architecture OBE v1.0

OBE means **Optimization-Based Engine**.

OBE is a WordPress optimization and automation engine. It is not only a website builder, chatbot, SEO plugin, translation plugin, or auto-publish bot. The community edition is a public, GPL-compatible foundation for safe, reviewable optimization workflows.

## Product promise

Before anything changes, OBE must answer:

1. What will happen?
2. What data is used?
3. What is generated?
4. What is risky?
5. Who approved it?
6. Where is the result stored?
7. Can it be reviewed before writing?

The default posture is `dry_run` first, `draft` or `needs_review` first, and `approval_required` before writes.

## Public/private boundary

Community Core may include public-safe contracts, UI shells, provider settings, AI Engine contracts, Responses API integration, Library, Activity, dry-run, approval, source preview, field mapping, template workflow runtime, and addon registry concepts.

Community Core must not include private project details, private prompts, private endpoints, private field maps, private workflows, private adapter logic, credentials, tokens, production data, client-specific business rules, hidden auto-publish behavior, destructive automation, or proprietary provider logic that cannot be distributed under the repository license.

Use generic public labels such as:

- Partner API Source
- Travel Content Source
- Accommodation Data Source
- Affiliate Data Source
- Product Data Source
- Private Project Adapter

## Admin information architecture

WordPress must expose one top-level OBE menu:

```text
OBE
├── Dashboard
├── Library
├── Auto Post / Import
├── Workflow
├── Addons
├── Activity
└── Settings
```

Addons are integrated inside OBE, not separate top-level WordPress admin menus. The Addons page contains:

- SEO Audit & Fix
- Performance Audit
- Auto Content / Auto Post
- Translation
- Workflow Pro / Agent Builder Style Workflow

## Core layers

```text
OBE
├── Admin UI Layer
├── AI Engine Layer
├── Provider Layer
├── Source Layer
├── Library Layer
├── Workflow Layer
├── Safety Layer
├── Addon/Module Layer
├── Activity Layer
├── Data Layer
└── Integration Layer
```

No module may bypass Safety, Library, Provider, or Activity responsibilities.

### Admin UI Layer

Owns the WordPress admin cockpit: dashboard, settings, library list/detail, Auto Post / Import screens, Workflow screens, Addons, Activity, and approval screens. Admin UI must call service layers rather than directly calling AI providers or writing posts.

### AI Engine Layer

Target folder: `includes/AI/`.

AI Engine is not the Provider Layer. It owns task type, model profile, reasoning effort, verbosity, prompt contract, structured output schema, response normalization, usage tracking, redaction, and error handling.

Target classes may include `AI_Engine`, `AI_Request`, `AI_Response`, `AI_Task_Type`, `Model_Profile`, `Prompt_Template`, `Prompt_Builder`, `Structured_Output`, `Usage_Record`, and `AI_Error`.

### Provider Layer

Target folder: `includes/Providers/`.

Provider Layer connects AI Engine to OpenAI, Gemini, and a custom OpenAI-compatible provider. It translates normalized OBE requests into provider-specific HTTP calls and maps provider-specific errors into OBE errors.

Provider Layer must not publish posts, create Library items directly, update metadata directly, or store unredacted logs.

### Source Layer

Accepts pasted text, CSV, XLSX, spreadsheet export, Partner API Source, future Google Sheet connector, and Private Project Adapter sources. The public community labels must remain generic.

Pipeline:

```text
intake → preview → detect columns → validate rows → map fields → save source preview → create Library import preview
```

### Library Layer

Everything generated by OBE must land in Library before writing. AI output must follow:

```text
AI output → Library → review → approval → writer
```

### Workflow Layer

Minimum runtime:

```text
input → guardrail → classify → validate → plan → dry-run → approval → write → log → end
```

Community runtime is template-based. No visual builder, autonomous background worker, or destructive operation is included in Community Core.

### Safety Layer

Applies operation classification, dry-run, approval, redaction, and write gates across all modules.

Operation classes:

- read
- preview
- plan
- generate
- write
- publish
- destructive

Global rules:

- dry-run first
- `draft` / `needs_review` first
- no hidden auto-publish
- no raw key display
- no write without approval
- no destructive actions in Community

### Addon/Module Layer

Addons are OBE modules under `OBE → Addons`. They extend documented contracts instead of private internals.

Addon scopes:

- community
- basic
- pro
- private_adapter

### Activity Layer

Records important provider, source, mapping, validation, Library, AI, approval, and write events. It must redact raw API keys, tokens, private prompts, private endpoints, credentials, and large raw private payloads.

### Data Layer

Start simple:

- WordPress options for settings and feature flags
- private CPT for Library items
- post meta for Library metadata, approval status, and source references

Custom tables may be introduced later for workflow runs, activity logs, batch jobs, or large source imports after feature shape is stable.

### Integration Layer

Integration code bridges WordPress, provider clients, future connectors, and public addon contracts. Integrations must respect Safety, Library, Activity, and public/private boundaries.

## Auto Post / Import architecture

User-facing workflow:

```text
Spreadsheet / Excel / CSV / Partner API
→ source intake
→ source preview
→ field mapping
→ validation
→ research plan
→ draft plan
→ generate
→ improve
→ dry-run
→ approval
→ write draft/needs_review
→ publish only after approval
```

Required generic fields:

- title
- slug
- target_keyword
- category
- location
- audience
- intent
- notes
- source_url
- image_hint
- target_post_type
- custom_meta
- taxonomy
- status

Only an approved `content_draft` can be written. Default write status is `draft`, or `needs_review` where available. Never publish automatically.

## UI design system summary

Use WordPress-native admin style.

- default page max-width: `1180px`
- form/settings max-width: `960px`
- table/list max-width: `1280px`
- card padding: `20px`
- card gap: `16px`
- section gap: `24px`
- primary button height: `36px`
- small button height: `30px`
- regular input width: `420px`
- long input width: `640px`
- textarea max-width: `760px`

Components: page header, card, grid, status badge, action bar, form row, help text, empty state, table, detail panel, approval box, and risk notice.

Confirmation behavior:

- preview/read actions may run after capability checks
- generate actions must show cost/risk context where relevant
- writes require a dry-run result and explicit approval
- publish requires separate explicit approval
- destructive actions are disabled in Community

## Security strategy

Hardening/security audit is final-stage, but minimum WordPress safety is required from the start:

- capability checks
- nonces for writes
- input sanitization
- escaped output
- masked API keys
- no raw key display
- no direct publish
- no destructive defaults

Final hardening later includes full capability, nonce, SQL, REST permission, file upload, log redaction, rollback, rate limiting, and dependency audits.
